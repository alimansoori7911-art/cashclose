> این پرامپت رو کامل به Claude Code بده. اسناد PRD اصلی (`cashclose_docs.docx` / `cash_close_Docs.pdf`) و فایل نمونه واقعی صندوق (`صندوق 3.xlsm`) رو هم در پوشه `docs/` پروژه قرار بده و به Claude Code بگو قبل از شروع کدنویسی این‌ها رو کامل بخونه — منبع حقیقت (source of truth) برای جزئیات کسب‌وکار، API Spec، DB Schema، Business Rules، Edge Cases و Acceptance Criteria همون اسناده. این پرامپت فقط تصمیمات معماری، فازبندی و **تغییرات نسبت به PRD اصلی** رو مشخص می‌کنه.

## ۳. تغییرات و افزوده‌های نسبت به PRD اصلی (این‌ها را جایگزین/مکمل بخش‌های متناظر در سند اصلی کن)

### ۳.۱ معماری چندمستأجری (SaaS Multi-tenant)
PRD اصلی تک‌مستأجری فرض شده؛ این پروژه **SaaS چندمستأجری** برای چند کسب‌وکار مختلفه:

- جدول جدید `tenants` (id, name, status, created_at) بالای `stores` اضافه کن. هر `store` یک `tenant_id` داره.
- برای جلوگیری از JOIN زنجیره‌ای در هر کوئری، `tenant_id` رو **دنورمالایز و مستقیم** روی `users`, `cash_registers` هم نگه دار (علاوه بر رابطه از طریق branch/store).
- جداسازی داده: یک دیتابیس مشترک + فیلتر `tenant_id` در تمام کوئری‌ها (نه schema-per-tenant). این فیلتر باید در یک لایه مرکزی (مثلاً Prisma middleware یا NestJS Guard/Interceptor) اعمال بشه، نه به‌صورت پراکنده در هر Controller — تا ریسک نشتی داده بین تنانت‌ها صفر بشه.
- **Super Admin پلتفرمی و Billing/Subscription در این فاز پیاده‌سازی نمی‌شن**، ولی مدل داده (enum نقش‌ها، جدول tenants) باید طوری طراحی بشه که بعداً بدون Migration مخرب قابل اضافه‌شدن باشن (مثلاً `role` enum رو طوری بنویس که افزودن `super_admin` بعداً فقط یک مقدار جدید اضافه کنه).

### ۳.۲ نسخه‌گذاری (Versioning) برای فلوی رد/اصلاح صندوق
در PRD اصلی، حسابدار باید بتونه «نسخهٔ Reject شده و نسخهٔ اصلاح‌شده رو کنار هم با تفاوت‌ها ببینه»، اما جدول `cash_register_history` فقط status و comment رو ذخیره می‌کنه، نه خودِ داده تراکنش‌ها — این یعنی دیف واقعی قابل ساخت نیست. **رفع:**

- یک جدول `cash_register_versions` اضافه کن: `id, cash_register_id, version_number, payload JSONB (کل ساختار تراکنش‌ها در لحظه submit), submitted_at, created_by`.
- هر بار که صندوقدار صندوق رو submit/close می‌کنه (چه بار اول چه بعد از اصلاح پس از reject)، یک رکورد جدید این‌جا ذخیره کن.
- صفحه حسابدار باید بتونه دو نسخه رو انتخاب و به‌صورت Side-by-side یا Diff (فیلدهایی که مقدارشون فرق کرده Highlight بشه) نمایش بده.

### ۳.۳ فراموشی رمز عبور
در Flow ذکر شده ولی در API Spec سند نبود. پیاده‌سازی کن:
- `POST /auth/forgot-password` (دریافت username/email → ارسال لینک reset با توکن یک‌بارمصرف و منقضی‌شونده)
- `POST /auth/reset-password` (توکن + رمز جدید)
- اگر ایمیل/SMS Provider در این فاز آماده نیست، لینک reset رو در فاز توسعه فقط در لاگ/Response نمایش بده و به‌صراحت اعلام کن که اتصال واقعی ایمیل/پیامک باید بعداً وصل بشه.

### ۳.۴ اعلان داخل‌برنامه‌ای (In-app Notification)
آیکون Notification در Top Navbar (طبق UI/UX سند) باید واقعاً کار کنه:
- جدول `notifications` (id, user_id, tenant_id, type, message, related_cash_register_id, is_read, created_at).
- وقتی حسابدار صندوقی رو رد می‌کنه → یک نوتیفیکیشن برای صندوقدار مربوطه ساخته بشه.
- فقط In-app (Polling ساده یا WebSocket اختیاری) — **بدون SMS/تلگرام/ایمیل خودکار** (طبق Out of Scope اصلی).

### ۳.۵ خروجی تصویری/PDF خلاصه صندوق
بعد از بستن صندوق، دکمه‌ای برای گرفتن یک تصویر (PNG/JPG) یا PDF از خلاصه صندوق (شبیه فرمت `صورتجلسه فروش` در فایل اکسل نمونه) اضافه کن تا صندوقدار/مدیر بتونه دستی در گروه (واتس‌اپ/تلگرام) بفرسته. **ارسال خودکار نیست، فقط تولید و دانلود فایل.**

### ۳.۶ سیاست نگهداری داده
- بدون حذف خودکار. حداقل ۶ ماه، حداکثر تا ۵ سال داده باید در دسترس و با کارایی مناسب بمونه.
- طراحی ایندکس و Pagination باید برای مقیاس ~۲ میلیون رکورد تراکنش (بر پایه ۲۰ صندوق × ۲۰ تراکنش × روزهای سال × تا ۵ سال، برای هر تنانت با ۵۰ شعبه) بدون افت محسوس جواب بده.

### ۳.۷ کتابخانه کامپوننت مشترک فرانت (از بخش DoD سند اصلی)
از همون فاز Setup این کامپوننت‌های Reusable رو به‌عنوان زیرساخت بساز (نه بعداً پراکنده در هر صفحه):
`DataTable` (با pagination/sort/filter)، `ImageUploader` (چندعکسی، پیش‌نمایش، فشرده‌سازی سمت کلاینت، حذف بدون رفرش)، `NumberInput` (فرمت هزارگان، ورودی فقط مثبت)، `FilterBar`، `JalaliDateRangePicker`، `Modal`، `StatusBadge` (تراز/مازاد/کسری با رنگ سبز/آبی/قرمز طبق PRD).

## ۴. خلاصه نقش‌ها و دسترسی‌ها (منبع کامل: بخش ۳ PRD)

| نقش | کلید |
|---|---|
| صندوقدار (Cashier) | ساخت/ثبت/Draft/بستن صندوق روزانه؛ فقط صندوق باز خودش |
| حسابدار (Accountant) | فقط Read روی صندوق‌ها + تایید/رد (با comment اجباری در رد) + مقایسه چند روز؛ نمی‌تونه بسازه/ویرایش کنه |
| مدیر مالی (Financial Manager) / مالک (Owner) | گزارش‌های کلان فروش/دریافتی/چک و آرشیو فایل‌ها؛ Owner علاوه‌براین باید بتونه صحت کار حسابدار، مدیر مالی و صندوقدار رو هم رصد کنه (یعنی Owner یک لایه Read دسترسی بیشتر از Financial Manager روی گزارش عملکرد کاربران داره) |
| مدیر فروشگاه (Store Manager) | تعریف فروشگاه/شعبه/کاربران/کارتخوان‌ها، فقط Read روی صندوق‌ها، نمی‌تونه تایید/رد کنه |

## ۵. فرمول هسته‌ای محاسبات (منبع: فایل اکسل واقعی + بخش ۱۱ PRD — دقیقاً همینو پیاده کن)

```
مانده صندوق =
    (فروش‌کل + دریافت‌بیعانه + دریافت‌بدهی + دریافت‌هزینه + مازاد‌صندوق
     + صدور‌سند‌بستانکاری + صدور‌سند‌اعتباری)
  − (تهاتر + دریافت‌سند‌بستانکاری + پرداخت‌هزینه + برگشت‌کالا
     + کسری‌صندوق + خرید‌بدون‌تسویه + بیعانه‌ازقبل + تخفیف‌VIP)

جمع اسناد =
    جمع(چک‌ها) + جمع(کارتخوان‌ها — همه دستگاه‌ها) + جمع(کارت‌به‌کارت)
  + نقدی + ارز(به‌ریال، صندوقدار خودش تبدیل و در توضیح مبلغ/نوع ارز را می‌نویسد)
  + درگاه فروش اینترنتی

اختلاف = جمع‌اسناد − مانده‌صندوق
  اختلاف = ۰   → تراز (سبز) → صندوق قابل بستن
  اختلاف > ۰   → مازاد (آبی)
  اختلاف < ۰   → کسری (قرمز)
  اختلاف ≠ ۰   → بستن صندوق غیرمجاز (فقط Save Draft مجازه)
```

این فرمول دقیقاً باید هم در Backend (validation قطعی قبل از close) و هم در Frontend (نمایش Real-time حین تایپ) پیاده بشه — منطق نباید فقط سمت فرانت باشه.

## ۶. فازبندی اجرا (هر فاز = یک PR/Commit مجزا با تست)

### فاز ۰ — Setup
مونوریپو یا دو ریپو (backend/frontend)، NestJS + Prisma + PostgreSQL، React+Vite+TS، ESLint/Prettier، ساختار پوشه استاندارد (`modules/`, `common/`, `features/`)، فایل `.env.example`، کتابخانه کامپوننت مشترک (بند ۳.۷).
**تست:** هر دو سرویس بالا میان، health-check endpoint جواب می‌ده، فرانت به بک‌اند وصل می‌شه.

### فاز ۱ — Auth + چندمستأجری + نقش‌ها
مدل `tenants`, `users`, JWT login/me/logout، forgot/reset password (بند ۳.۳)، Guard مرکزی تفکیک tenant، ۴ نقش با Route Guard جدا.
**تست:** لاگین هر نقش، تلاش دسترسی غیرمجاز → 403، دو تنانت مختلف داده هم رو نمی‌بینن.

### فاز ۲ — مدیریت فروشگاه
CRUD کامل Store/Branch/Users/POS Terminals، تخصیص کارتخوان به صندوقدار، صفحه لاگ عملیات (فقط نمایش).
**تست:** مدیر فروشگاه یک شعبه و ۲ کارتخوان و یک صندوقدار می‌سازه؛ صندوقدار فقط کارتخوان‌های شعبه خودش رو می‌بینه.

### فاز ۳ — هسته صندوق روزانه (مهم‌ترین فاز)
مدل `cash_registers` + `transactions` (unified، `meta JSONB`) + `cash_register_versions` (بند ۳.۲)، فرم کامل بخش‌های A تا K (فروش کل، برگشتی، کارتخوان‌های متعدد، نقدی، چک، کارت‌به‌کارت، بیعانه، هزینه، اسناد بستانکاری/اعتباری، تهاتر، ارز)، موتور محاسبه (بند ۵)، Save Draft با auto-save، قفل ساخت صندوق جدید تا نبستن روز قبل، بستن دو روز همزمان.
**تست:** تمام Edge Case‌های بخش ۱۲ PRD (قطع اینترنت حین Save، صندوق دوم برای یک روز، اختلاف≠۰ در close، حذف عکس بعد از submit) دستی یا با تست خودکار پوشش داده بشن.

### فاز ۴ — آپلود عکس
Storage Adapter (بند ۲)، چندعکسی، compress سمت کلاینت، محدودیت ۵ عکس/حداکثر ۳MB هر عکس، حذف فقط در حالت draft.
**تست:** آپلود ۵ عکس روی یک فیلد، رد عکس ششم، رد فایل >۳MB.

### فاز ۵ — فلوی حسابدار
لیست با فیلتر پیشرفته (تاریخ/بازه/شعبه/صندوقدار/مبلغ)، تایید/رد (comment اجباری در رد)، نمایش Diff نسخه رد‌شده/اصلاح‌شده (بند ۳.۲)، مقایسه چند روز، نوتیفیکیشن به صندوقدار (بند ۳.۴).
**تست:** رد یک صندوق → صندوقدار نوتیف می‌گیره → اصلاح و ارسال مجدد → حسابدار Diff دو نسخه رو می‌بینه.

### فاز ۶ — داشبورد مدیر مالی/مالک
گزارش فروش روزانه/مازاد‌کسری/صندوق‌های باز‌رد‌شده، نمودار روزانه/ماهانه/سالانه، پیش‌بینی فروش ماه (میانگین تا امروز × روزهای باقی‌مانده)، مقایسه سال‌به‌سال، مقایسه بین شعب، خروجی Excel، خروجی تصویری/PDF خلاصه صندوق (بند ۳.۵)، لایه دید اضافه Owner روی عملکرد کاربران.
**تست:** گزارش‌ها با فیلتر تاریخ درست جواب بدن، Export اکسل باز و صحیح باشه.

### فاز ۷ — امنیت، لاگ، کارایی
Audit trail کامل روی تغییر وضعیت صندوق، rate limiting، sanitize کردن `meta` JSON، ایندکس‌های الزامی (بند ۱۴.۲ PRD)، تست حجم بالا (۲۰ صندوق هم‌زمان طبق بند ۱۴.۴ PRD).
**تست:** Load test ساده، بررسی زمان پاسخ APIهای اصلی زیر ۷۰۰ms و گزارش‌ها زیر ۳ ثانیه.

### فاز ۸ — Docker + CI/CD + مستندسازی
Dockerfile برای backend/frontend، docker-compose (dev/staging/prod)، GitHub Actions (build→test→deploy)، Swagger/OpenAPI برای API، ERD مستند، راهنمای نصب و اجرا، `.env` variables مستند.
**تست:** `docker-compose up` کل پروژه رو از صفر بالا میاره.

## ۷. قوانین کاری برای Claude Code در طول پروژه

1. قبل از هر فاز، اگر جزئیاتی در PRD یا این پرامپت نبود (مثلاً دقیق‌ترین رفتار یک Edge Case)، بپرس — پیش‌فرض نساز.
2. کد هر فاز باید مستقل قابل اجرا و تست باشه؛ فاز بعد رو شروع نکن مگه من تایید بدم.
3. Business Rules بخش ۱۱ PRD (به‌خصوص قوانین صندوقدار و حسابدار) باید هم در Backend Validation و هم در UI (Disable شرطی دکمه‌ها) اعمال بشن — نه فقط یک‌طرفه.
4. برای هر فاز، لیست کوتاهی از "چیزهایی که فرض کردم چون در سند نبود" بده.
5. کد فارسی/RTL: تمام متن‌های UI فارسی و راست‌چین، اعداد با جداکننده هزارگان، تاریخ‌ها جلالی.
