# راهنمای بهره‌برداری

آنچه برای اجرا، پایش و عیب‌یابی سرویس در محیط واقعی لازم است.

---

## مسیرهای سلامت

| مسیر | برای چه | رفتار هنگام قطعی دیتابیس |
|---|---|---|
| `GET /api/v1/health` | نمای کلی برای انسان | `200` با `status: degraded` |
| `GET /api/v1/health/live` | ارکستراتور: پروسه زنده است؟ | `200` — دیتابیس را نمی‌خواند |
| `GET /api/v1/health/ready` | Load Balancer: ترافیک بفرستم؟ | `503` |

**چرا دو مسیر جدا:** اگر `live` هم دیتابیس را چک می‌کرد، یک قطعی موقت
دیتابیس باعث می‌شد ارکستراتور **همهٔ** نمونه‌ها را ری‌استارت کند —
درحالی‌که مشکل از سرویس نیست. `ready` ترافیک را قطع می‌کند ولی پروسه
زنده می‌ماند و به‌محض بازگشت دیتابیس دوباره وارد چرخه می‌شود.

هیچ‌کدام توکن نمی‌خواهند (`@Public`)، چون ابزار پایش پیش از احراز هویت
باید بتواند وضعیت را بخواند.

## پیگیری یک خطا

هر درخواست یک شناسه دارد که در سه جا دیده می‌شود:

1. **هدر پاسخ** `x-request-id`
2. **بدنهٔ خطا** در فیلد `requestId`
3. **لاگ سرور** در ابتدای خط

کاربر در خطاهای سمت سرور (۵xx) هشت رقم اول را روی صفحه می‌بیند:

```
خطای غیرمنتظره در سرور رخ داد. (کد پیگیری: 3f2504e0)
```

برای یافتن همان درخواست در لاگ:

```bash
grep "3f2504e0" server.log
```

اگر سرویس پشت Gateway است و شناسه از بالادست می‌آید، همان مقدار حفظ
می‌شود — **به شرطی که قالب UUID داشته باشد**. مقدار دلخواه پذیرفته
نمی‌شود، چون متن آزادِ کلاینت مستقیم در لاگ می‌نشیند و می‌تواند خط لاگ
جعلی بسازد.

### قالب خط لاگ

```
[HTTP] [<شناسه>] GET /api/v1/cash-registers → 200 43ms کاربر=<شناسهٔ کاربر>
```

درخواست کندتر از یک ثانیه با سطح `warn` و برچسب «کندتر از حد انتظار»
ثبت می‌شود.

**بدنهٔ درخواست هرگز لاگ نمی‌شود.** بدنه‌ها حاوی رمز، توکن و مبالغ
مشتری‌اند؛ نوشتنشان در فایل لاگ یعنی نشت داده. متد، مسیر، وضعیت و زمان
برای عیب‌یابی کافی است.

مسیرهای پرتکرار و کم‌ارزش (سلامت و شمار اعلان‌های خوانده‌نشده) لاگ
نمی‌شوند تا درخواست‌های واقعی زیر انبوه نویز دفن نشوند.

## پیکربندی محیط تولید

`NODE_ENV=production` چند قاعدهٔ اضافی را فعال می‌کند که هنگام **بالا
آمدن** بررسی می‌شوند — نه وسط کار:

- `CORS_ORIGINS` نمی‌تواند `*` باشد.
- همهٔ مبدأها باید `https` باشند (توکن روی HTTP رمزنگاری‌نشده منتقل
  می‌شود).
- `JWT_SECRET` حداقل ۳۲ کاراکتر و بدون مقدار نمونهٔ `CHANGE_ME`.
- مستندات Swagger (`/api/docs`) سرو نمی‌شود.

اگر هرکدام نقض شود، سرویس با پیام فارسی روشن بالا نمی‌آید. این عمدی
است: خطای پیکربندی باید همان ثانیهٔ اول دیده شود، نه در اولین درخواست
کاربر.

## خاموشی تمیز

`app.enableShutdownHooks()` فعال است. با دریافت `SIGTERM`:

1. پذیرش درخواست جدید متوقف می‌شود،
2. درخواست‌های در جریان تمام می‌شوند،
3. Prisma اتصالش را می‌بندد.

برای سامانه‌ای که تراکنش مالی می‌نویسد این حیاتی است: قطع وسط کار یعنی
احتمال نیمه‌کاره ماندن نوشتن.

---

## دیتابیس قابل‌حمل (توسعه)

نصب PostgreSQL بدون دسترسی مدیر:

```bash
powershell -File scripts/pg-portable.ps1 start
```

`status` وضعیت و `stop` توقف. **در ابتدای هر جلسه باید دستی start
شود.** نکتهٔ مهم: `taskkill /IM node.exe` علاوه بر سرویس، پوستهٔ ناظر
دیتابیس را هم می‌کشد — به‌جایش فقط PID سرویس را متوقف کنید.

## محدودیت نرخ

| مسیر | سقف |
|---|---|
| ورود (`/auth/login`) | ۱۰ درخواست در ۶۰ ثانیه |
| بازیابی رمز | ۵ در ۶۰ ثانیه |
| بقیهٔ مسیرها | `RATE_LIMIT_MAX` (پیش‌فرض ۱۲۰) در ۶۰ ثانیه |

علاوه بر این، قفل حساب پس از `LOGIN_MAX_ATTEMPTS` تلاش ناموفق به‌مدت
`LOGIN_LOCKOUT_MINUTES` دقیقه اعمال می‌شود.

هنگام اجرای پشت‌سرهم تست‌های انتها‌به‌انتها این سقف فعال می‌شود؛ بین دو
تست یک دقیقه فاصله بیندازید.
